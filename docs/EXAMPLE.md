# A worked example: find a function, port it, prove it

Everything else in this kit is about *your* game, which nobody can give you. This page is the one place
you can do the whole loop today, on a game that does not exist.

`kit demo` assembles one: a boot ELF of hand-written R5900 machine code, a raw overlay, and an ISO 9660
image holding both plus a `SYSTEM.CNF` with a made-up serial. In twenty minutes you will extract a disc,
find code in a blob, read it, call one of its functions with the oracle, port that function to Rust, and
prove the port bit-exact over ten thousand inputs — and then break it on purpose and watch the proof
catch it.

**Nothing here is game-derived.** Every byte under `context/demo/` is generated by `ps2kit/demo.py`:
the instruction words come from a 40-line assembler in that file, the weight table is eight floats chosen
to be awkward, the serial `SLUS-90001` is invented, and nothing is downloaded. No real game's code or
data is in this repository, in the generated demo, or in the outputs below. That is also why the demo is
safe to delete and regenerate at will.

Prerequisites: Python 3.11+ and a Rust toolchain. No emulator, no BIOS, no Ghidra, no disc.

Every console block below is real output from running the command above it, with two cosmetic edits:
long absolute paths are shortened to `…/context/demo/…`, and one long URL and two long failure dumps are
trimmed with a `…`. (The generated config holds absolute paths on purpose, so that the Python tools —
which resolve relative paths against the repository — and the Rust crates — which resolve them against
`$KIT_ROOT` — cannot disagree about where anything is.)

> In a hurry, or checking a fresh clone still works? `kit demo --check` does every step on this page and
> prints one pass/fail line each, in about half a second. Come back for the reasoning.

## 1. What is on the disc

```console
$ kit extract --list
demo.iso  (2048-byte sectors)  volume 'KITDEMO'  SLUS-90001  boot SLUS_900.01  ver 1.00
3 files, 9 KB
     LBA        bytes  path
      24        8704  DEMO/OVERLAY.BIN
      23         924  SLUS_900.01
      22          57  SYSTEM.CNF
```

The serial is not decoration. `SYSTEM.CNF` names the file the console boots (`BOOT2 =
cdrom0:\SLUS_900.01;1`), and that filename *is* the disc's serial. Every address you write down for the
rest of the project is only true for one build of one region, so the kit checks the disc against
`[game] serial` before it does anything, and refuses when they disagree:

```console
$ kit extract --list --iso context/demo/other-game.iso
kit extract: this disc is SLUS-20000, but kit.toml says [game] serial = 'SLUS-90001'.
  image: context/demo/other-game.iso
Extracting the wrong region leaves every address in your notes wrong. Either point
[game] iso at the right dump, fix [game] serial, or pass --any-serial if you mean it.
```

That refusal is the single most valuable check in the kit, because the failure it prevents is silent:
the wrong dump extracts perfectly happily and then every address is off by an unknowable amount.

Now unpack it:

```console
$ kit extract
demo.iso  (2048-byte sectors)  SLUS-90001  boot SLUS_900.01  ver 1.00
extracting 3 file(s), 9 KB → context/demo/iso
done: 3 files, 9 KB
largest: DEMO/OVERLAY.BIN 8 KB, SLUS_900.01 924 B, SYSTEM.CNF 57 B
next: kit elf            # build the Ghidra inputs (--scan guesses the overlays)
```

## 2. Find the code

A PS2 game is one boot ELF plus, nearly always, a pile of raw blobs it loads over each other at fixed
addresses — overlays. The ELF is easy: it says where it goes. The blobs say nothing at all, and until you
know where one loads, every address in it is meaningless.

`kit elf --scan` works it out from the code itself:

```console
$ kit elf --scan
Files that look like raw MIPS code (opcode density, prologue density, and how many of the
file's own jal targets land inside [load, load+size) — that is what pins the load address):
* DEMO/OVERLAY.BIN                   8 KB  opcodes 100%  prologues 30.1/KB  jal   256 in-range 100%  load 0x0200000

Paste into kit.toml (check the names — they become the dump names and `-p` arguments):

[[overlay]]
name = "overlay"
file = "DEMO/OVERLAY.BIN"
load = "0x200000"
# off = 0   # the file starts with a loader header; the whole file is copied to `load`

Then:  kit elf   &&   kit ghidra analyse
```

Three signals, and it is worth knowing why each one works:

- **opcodes 100 %** — nearly every 32-bit word decodes to a plausible MIPS instruction. Textures and
  audio score far lower.
- **prologues 30.1/KB** — that many `addiu $sp, $sp, -N` words, which is what the start of a function
  looks like. Density tells you this is a lot of small functions, i.e. compiled code.
- **jal 256, in-range 100 %** — the decisive one. A `jal` encodes an *absolute* target, so a blob's
  internal calls all point at wherever it was linked to live. Try candidate bases, keep the one that
  captures the most targets, and the load address falls out: `0x200000`.

The scan also noticed that the first word of the file equals that address — a loader header naming
itself — and hints at `off`. It can only hint: the header's *length* is known to the loader, not to the
file. Here it is `0x100` bytes, and the generated `kit.toml` already says so. On a real game you read
that number out of the loader function, and getting it wrong shifts every address in the overlay by a
constant, which is a confusing afternoon.

With the config right, build one ELF per program so Ghidra (and `kit dis`) have something to open:

```console
$ kit elf
Kit Demo (synthetic): building 2 program(s) into …/context/demo/elf
  boot   boot.elf               1 KB  entry 0x1000c0  2 segments
  extra  extra.elf              8 KB  at 0x200000 + 2 boot segment(s)
next: kit ghidra analyse        # tens of minutes per program, once
```

Note what `extra.elf` is: the overlay's code *plus* the boot ELF's segments. An overlay calls into the
boot program constantly, and a decompiler that cannot see those targets produces a function full of
`(*(code *)0x1004a0)()` instead of a call.

## 3. Read it

Ghidra gives you C; `kit fn` and `kit xref` then print it a function at a time. This walkthrough
skips it — the analysis takes tens of minutes and Ghidra may not be installed — and reads the
instructions directly instead, which for a function this size is what you would do anyway:

```console
$ kit dis @blend_weights --len 0x40 -p boot
# boot  00100080..001000c0  (16 instructions, ordinary MIPS via llvm-mc)
00100080  3c080010  lui	$8, 16
00100084  25080400  addiu	$8, $8, 1024
00100088  24090008  addiu	$9, $zero, 8
0010008c  44802000  mtc1	$zero, $f4
00100090  44803000  mtc1	$zero, $f6
00100094  c5020000  lwc1	$f2, 0($8)
00100098  460c1082  mul.s	$f2, $f2, $f12
0010009c  46022100  add.s	$f4, $f4, $f2
001000a0  25080004  addiu	$8, $8, 4
001000a4  2529ffff  addiu	$9, $9, -1
001000a8  1d20fffa  bgtz	$9, -20    ; -> 0x100094
001000ac  00000000  nop
001000b0  46062018  adda.s    $f4, $f6
001000b4  460c601c  madd.s	$f0, $f12, $f12
001000b8  03e00008  jr	$ra
001000bc  00000000  nop
```

`adda.s` is spaced differently from the lines around it, which is not a typo: `llvm-mc` does not know
that instruction, so the kit decodes it — along with the rest of the R5900's extras (`madd.s`'s siblings,
`lq`/`sq`, the MMI set, the VU0 macro ops) — itself. This matters more than cosmetics: a general MIPS
disassembler silently *drops* words it cannot decode, which is how a port ends up missing exactly the
arithmetic that made the original unusual. `kit dis` prints every word, one line each, always.

`@blend_weights` is a `[symbols]` entry; anywhere the kit takes an address it also takes `@name`,
`0x100080` or `100080`. Reading it:

- `lui`/`addiu` build `0x00100400` in `$8` — a pointer to something in `.data`. Two halves, because that
  is how MIPS loads a 32-bit constant. The low half is sign-extended, so a compiler adds 1 to the high
  half when it is negative; miscopying that is a classic way to end up reading the wrong table.
- `$9 = 8`: a loop counter. Eight of something.
- `$f12` is the first float argument, and it is never written — it is `x`.
- The loop: load a float, `mul.s` by `x`, `add.s` into `$f4`. A running sum, front to back.
- `adda.s $f4, $f6` with zero in `$f6` moves the sum into the FPU's accumulator, and `madd.s $f0, $f12,
  $f12` adds `x * x` to it and returns that in `$f0`.

Whatever is at `0x00100400`, there are eight of them and they are floats. Read them:

```console
$ kit data @weights 0x20 --as f32 -p boot
# boot  00100400  32 bytes as f32
+0x0000  00100400               1           0.25      0.3333333        0.00075
+0x0010  00100410          1024.5      0.0078125          3e-05       12.34568
```

Read the table out of the image, never out of a decompiler's rendering of the literals. The image is the
truth; a table typed by hand is a table with a typo in it.

One more thing worth doing early, because it is nearly free and sometimes decides a whole week: look for
strings. Debug text is the best foothold a port ever gets — it names the original's own concepts.

```console
$ kit data --strings demo -p boot
# boot  3 strings matching 'demo'
00100440  demo: gear %d step %d
00100457  demo: blend %.3f
00100469  DEMO BOOT 1.00
```

## 4. Call it, before you port it

You now have a theory about what the function does. The oracle tests the theory in one line: it loads the
program's code into a small R5900 interpreter, puts your argument in `$f12`, runs the instructions, and
tells you what came back.

```console
$ kit oracle blend_weights --floats 2.5
blend_weights 0x00100080  (…/context/demo/oracle.txt)
args    2.5
steps   65
v0      0x0  0  (as a float: 0)
f0      2602.3438  0x4522a580
```

Sixty-five instructions, no emulator, no BIOS, 40 ms. Check it by hand: the weights sum to
`1038.4376…`, times `2.5` is `2596.09…`, plus `2.5 * 2.5` is `2602.34…`. The theory holds.

The integer functions work the same way, and the call that one of them makes to the other happens for
real inside the interpreter:

```console
$ kit oracle step_for_gear --ints 5
step_for_gear 0x00100040  (…/context/demo/oracle.txt)
args    0x5
steps   24
v0      0x19  25
f0      0  0x00000000
wrote   0x01ffbff0..0x01ffbff4  f0 ff ff ff
```

`25` is `STEPS[5]`. The `wrote` line is the function spilling `$ra` to its stack frame, which the oracle
reports because *what a function writes* is often the only output that matters — a function that fills a
struct returns nothing at all.

Names come from `context/demo/oracle.txt`, the demo's own addresses file (`[oracle] addresses` in its
`kit.toml`), so practising here never touches the addresses file of your real project. On your own game
you would add one with `kit oracle add blend_weights 0x100080`.

## 5. Port it

```rust
/// The weight table the original reads, as eight floats in its `.data`.
pub const WEIGHTS: [f32; 8] = [1.0, 0.25, 0.3333333, 7.5e-4, 1024.5, 0.0078125, 3.0e-5, 12.345679];

pub fn blend_weights(x: F) -> F {
    let mut sum = f(0.0);
    for &w in &WEIGHTS {
        // mul.s then add.s, in that order, into the same register the next term reads.
        sum += F(w) * x;
    }
    // adda.s $f4, $f6 with a zero in $f6 — "ACC = sum" — then madd.s: ACC + chop(x * x).
    sum.madd(x, x)
}
```

The whole thing is in [`crates/game-sim/src/demo.rs`](../crates/game-sim/src/demo.rs), with the two
integer functions for company. Four decisions in nine lines, and every one of them is the difference
between a port and a lookalike:

1. **`F`, not `f32`.** `F` is `ps2-float`'s model of the EE's FPU: it chops where IEEE rounds to nearest,
   it keeps one guard bit when aligning exponents for an add, and it saturates where IEEE makes an
   infinity. The module begins with `#![deny(clippy::float_arithmetic)]`, so a stray `+` on a bare `f32`
   is a clippy *error* — which is a gate in `kit done`, and a step in `kit demo --check`. Section 7
   shows it firing.
2. **The original's order.** Front to back, one accumulator. `WEIGHTS.iter().map(|w| w * x).sum()` is the
   same arithmetic in a different order, and chopped addition is not associative, so it is a different
   number.
3. **`madd` for `madd.s`.** The PS2's `madd.s` is *not* a fused multiply-add: it chops the product to
   `f32` and only then runs it through the adder. `F::madd` models exactly that. Rust's `f32::mul_add`
   models a true FMA, which this hardware does not have, and `sum + x * x` models two separate
   operations — all three give different answers, and the disassembly is what tells you which one is
   right.
4. **The table was read, not retyped.** Copied from the `kit data` output above.

## 6. Prove it

```rust
for k in 0..10_000 {
    let x = rng.input(k, 4096.0);                           // fixed awkward values first, then random
    ee.call(at, &[], &[x], 10_000);                         // the original's own instructions
    let (got, want) = (ee.f0(), demo::blend_weights(F(x)).to_f32());
    assert!(got.to_bits() == want.to_bits(), "blend_weights({x} = {:#010x}) differs …", x.to_bits());
}
```

The whole file is [`crates/game-sim/tests/demo.rs`](../crates/game-sim/tests/demo.rs). It needs no disc,
so it runs in CI and on a fresh clone: if `context/demo/` is missing, the test runs `kit demo` itself.

```console
$ cargo test -p game-sim --test demo -- --nocapture --test-threads=1
running 5 tests
test an_overlays_function_can_be_proved_too ... overlay_mix: 10000 inputs, bit-exact
ok
test the_float_function_is_bit_exact_over_ten_thousand_inputs ... blend_weights: 10000 inputs, bit-exact
ok
test the_generated_game_is_really_there ... SLUS-90001: boot + 1 overlay(s), 32 MB of RAM, 5 named functions
ok
test the_integer_functions_match ... clamp_index, step_for_gear: 10000 inputs each, exact
ok
test the_same_function_in_host_f32_is_a_different_function ... host f32 first differs at input 2: blend_weights(1 = 0x3f800000)
  the game gives 1039.4374 (0x4481edff)
  host f32 gives 1039.4376 (0x4481ee01)
  8423 of 10000 inputs differ (84%)
ok

test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.02s
```

Three details in that run that are the point of the whole method:

- **Ten thousand inputs, bit-exact, in hundredths of a second.** There is no tolerance to argue about,
  because the comparison is against the instructions themselves.
- **The generator goes where play does not.** Zero, negative zero, `±4096`, the smallest nonzero float,
  then random values across four magnitudes. A recording of real play visits a thin slice of that and
  misses the branch that only fires at exactly zero.
- **The integer functions passed first try.** That is normal, and it is why float code deserves the
  attention: reading integer code correctly is usually enough, and reading float code correctly is not.

## 7. Now break it

Rewrite the same function with host arithmetic — the port anyone writes on their first day:

```rust
pub fn blend_weights(x: F) -> F {
    let x = x.to_f32();
    let mut sum = 0.0f32;
    for &w in &WEIGHTS {
        sum += w * x;
    }
    F(sum + x * x)
}
```

Two things happen. First, it does not survive the lint, which is the cheapest of the two:

```console
$ cargo clippy -p game-sim
error: floating-point arithmetic detected
  --> crates/game-sim/src/demo.rs:79:9
   |
79 |         sum += w * x;
   |         ^^^^^^^^^^^^
   |
   = help: for further information visit https://rust-lang.github.io/rust-clippy/…#float_arithmetic
note: the lint level is defined here
  --> crates/game-sim/src/demo.rs:12:9
…
```

(Trimmed: a second copy of the same error for the `F(sum + x * x)` line, and an unused-import warning,
because the honest port no longer needs `ps2_float::f`.)

And if you silence that, the proof catches it on the third input — which is `1.0`:

```console
$ cargo test -p game-sim --test demo
thread 'the_float_function_is_bit_exact_over_ten_thousand_inputs' panicked at crates/game-sim/tests/demo.rs:184:9:
blend_weights(1 = 0x3f800000) differs at input 2 of 10000
  the game gives 1039.4374 (0x4481edff)
  the port gives  1039.4376 (0x4481ee01)

test result: FAILED. 4 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
```

Two ulps. `0x4481edff` against `0x4481ee01`, on the most ordinary input imaginable — and 84 % of the ten
thousand inputs disagree. No screenshot, no tolerance and no "looks right" would ever have shown it.

That is the argument for all of this, and it is the test named
`the_same_function_in_host_f32_is_a_different_function`: it asserts that the host version *does* diverge,
early and often. Two ulps do not matter. Two ulps fed into an integrator for sixty frames put a ball on
the other side of a line, and every AI decision after that point is a different game. Bit-exactness is
not perfectionism — it is the only error bound that does not grow.

## 8. Write down what you could not prove

The last step of the loop, every time, and the one everybody skips. Four of the demo's five functions are
proved above. Here is the honest remainder for this example.

### Not verified / not 1:1

**Not proved here, at all:**

- **`demo_main`** is called by nothing and proved by nothing. It exists so `kit elf` has an entry point
  and so there is a real call graph; its behaviour is unchecked.
- **The loader header.** `off = 0x100` is taken from the generated config, not derived. The scan can only
  tell you that a header is probably there.
- **Timing and frame flow.** Nothing here runs a frame. The oracle has no concept of time, so everything
  the kit offers for state machines, animation, input latency and frame-order bugs — `kit record`,
  `kit probe`, `kit pine`, the vsync counter, save states — is untouched by this example. On a real
  port that is most of the work.
- **Anything needing the emulator.** No PCSX2, no BIOS, no live capture, no screenshots, no virtual
  controller. `docs/PCSX2.md` is the other half of the kit and this page does not open it.
- **Ghidra.** The walkthrough reads instructions with `kit dis`, not decompiled C. `kit ghidra
  analyse`, `kit fn`, `kit xref` and `--similar` all need a Ghidra project the demo does not build,
  because analysis takes tens of minutes and the function is sixteen instructions long.
- **The replay harness.** `game_sim::replay` is still the stub it ships as. Proving whole-simulation
  behaviour over a recorded session is the fourth proof method in `docs/PROVING.md` and the demo has no
  session to replay.

**Where the synthetic program is kinder than a real one, in ways that could mislead:**

- **It comes with symbols and an addresses file.** The generated ELF has a symbol table and
  `oracle.txt` names all five functions with a description. A real disc gives you none of that: you get
  `FUN_00100080` and work outwards from strings, call graphs and what the game does on screen. Naming
  functions *is* the reverse engineering; here it was done for you.
- **The functions are tiny and pure.** Sixteen instructions, arguments in registers, one float out, no
  globals, no structs, no pointers to patch, no RAM state. Real gameplay functions take a pointer to a
  200-byte object, read six globals and write most of their output through memory — which the oracle
  handles (`Ee::from_ram`, `hooks`, reading memory back), but which this example never shows.
- **The overlay is padded with filler.** 256 identical stub functions exist only so the blob is big
  enough for `kit elf --scan` to score honestly. A real overlay is thousands of real functions; the
  scan's percentages here are unrealistically clean (opcodes 100 %, in-range 100 %).
- **No compiler was involved.** The code was assembled by hand, so it has none of the things that make
  real PS2 code hard to read: no scheduled delay slots, no `$gp`-relative data access, no inlining, no
  tail calls, no leaf-function register allocation, and no VU0 macro-mode blocks — which in a real game
  do most of the vector maths, and need `ps2_float::Vf`, a *different* arithmetic model from the `F` used
  here (full-width adder, clamping instead of saturation). Mixing the two models up is the most common
  reason a port that "uses the PS2 float model" still drifts.
- **One region, one version, no revisions.** No `SLUS` vs `SLES` differences, no v1.01 that moves every
  address, no second disc.
- **The ISO is minimal.** A PVD, two directories, three files, 58 KB. No multi-track image, no 2352-byte
  sectors, no Joliet, no subdirectory depth, no 4 GB of streamed audio to skip past.
- **The weights were chosen to make the point.** `1024.5` next to `3.0e-5` makes the EE's one guard bit
  visible immediately. Real divergence is usually subtler and shows up later — which is an argument for
  more inputs, not fewer.

That list is the habit this project is built around: a port is "done" when you can say exactly what you
proved and exactly what you did not. `docs/WORKFLOW.md` has the journal format for writing it down.

## All of it at once

Every step above, as the kit's own integration test. It is the fastest way to find out whether a change
to the kit broke the disc reader, the overlay scan, the ELF builder, the disassembler, the table reader,
the oracle or the proof — and it needs nothing installed but Python and Rust.

```console
$ kit demo --check
the whole walkthrough, on the generated game in context/demo:

  ok    the disc reads, and its serial is the configured one                         extract --list
  ok    a disc with the wrong serial is refused                                      extract --list --iso context/demo/other-game.iso
  ok    the disc extracts                                                            extract
  ok    --scan finds the overlay and works out where it loads                        elf --scan
  ok    the programs build for Ghidra                                                elf
  ok    the float function disassembles                                              dis @blend_weights --len 0x40 -p boot
  ok    its weight table reads as floats                                             data @weights 0x20 --as f32 -p boot
  ok    the debug strings are where the strings reader can find them                 data --strings demo -p boot
  ok    the addresses file lists the five functions                                  oracle list
  ok    the oracle calls the original by name                                        oracle blend_weights --floats 2.5
  ok    the port is bit-exact against the original over 10,000 inputs (kit check)  check --no-gate
  ok    no host float arithmetic got into the port                                   cargo clippy -q -p game-sim --all-targets

12/12 steps passed
```

It exits non-zero if any step fails, and prints the last twenty lines of whatever went wrong underneath
the failing line.
